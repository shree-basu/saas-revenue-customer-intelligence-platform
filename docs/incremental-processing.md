# Incremental fact publication (Day 5)

`fct_invoices`, `fct_product_usage_daily`, and `fct_support_cases` merge on validated non-null natural grains (`invoice_id`, deterministic account/product/date `usage_key`, and `case_id`). Every row in the **latest validated delivery** is selected on each run. There is deliberately no `updated_at > MAX(target.updated_at)` filter: a correction to an old invoice date or a late update with a non-increasing timestamp must still reach the merge. Retrying the same batch replaces matching rows rather than inserting duplicates; a genuinely new key is inserted. The feed is small in this local proof, so scanning all incoming rows is a correctness choice, not a measured performance optimization.

The `late-correction` synthetic scenario moves an existing invoice's business date backwards and revises its amount, while changing an existing usage measure. The integration check exercises initial publication, a new account, update of old natural keys, and retry. If a source *natural key* itself changes (for example, an account/product/day usage correction to a different day), the old key would remain and require a source tombstone or controlled backfill; this contract does not claim such deletion support. The loader replaces local raw tables for each delivery. Dimension tables remain latest-state full refresh, so incremental fact rows can retain old dimension keys whose members are absent from a later delivery; complete cross-batch dimensional retention is not yet implemented. Movement history requires its input feed to include all months being recomputed and is still full refresh.

`snap_account_history` is separate from `dim_account` and captures observed CRM account versions using dbt's timestamp strategy (`account_id`, `updated_at`). The local loader rejects an older revision for an account already seen and rejects a changed row with an unchanged timestamp; all nine raw-table replacements occur in one transaction. To rebuild an earlier time range, start a fresh isolated local database and process preserved immutable deliveries in **updated_at order**. A snapshot run against only the latest current-state batch cannot reconstruct unseen intermediate changes or arbitrary retroactive effective dates. Hard deletes are not inferred: disappearing accounts require a separate tombstone policy. The integration check confirms the second version's validity interval, a retry with no duplicate version, and rollback of an out-of-order load. [dbt snapshot documentation](https://docs.getdbt.com/docs/build/snapshots) explains the timestamp strategy.

The source contract rejects a new CSV column even when its manifest and hash are internally consistent. `on_schema_change='fail'` separately blocks unreviewed changes to an incremental model's top-level columns. It is not automatic schema evolution or historical backfill. A later approved contract version plus model migration or full refresh must handle intentional additions. [dbt incremental-model documentation](https://docs.getdbt.com/docs/build/incremental-models) explains the merge key and schema-change choices. No cloud warehouse has been executed.
